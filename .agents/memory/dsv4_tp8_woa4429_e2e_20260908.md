# TP8 M32 wo_a 4429: do not promote

## Scope and decision

Native AR, TP8/EP1, original weights, 1,048,576-token pool, fixed 32 distinct
code prompts. Candidate only matches gfx90a decode M32 with one attention group.
C1, prefill, speculative execution, other TP/EP shapes remain unchanged.
`SGLANG_DSV4_GFX90A_TP8_M32_WOA_HIPBLASLT` stays default-off. Baseline service
on port 30011 was restored with the candidate flag absent.

The standalone 4429 win did not translate into an evident service improvement.
This is a screening experiment, not a formal ABBA acceptance result.

| Path | C32 x 256 median output tok/s |
| --- | ---: |
| Prior formal control | 982.12644 |
| Initial candidate | 983.80864 |
| Candidate after initialization fix | 982.24221 |

Both candidate processes passed France C32; C1 France and six measured
256-token outputs matched the established C1 reference. This does not establish
general numerical parity: the standalone solution is non-bitexact versus Torch.

## Long-output evidence

Candidate: 32 requests x 2048 tokens, one wave, 920.72047 tok/s.
Fresh flag-off control: same workload, two waves, median 916.05776 tok/s.
All 96 requests completed 2048 tokens with finish=length. These differing wave
counts and dynamic batches cannot establish a throughput win.

After truncating token IDs at the first EOS (ID 1), the candidate Rust LRU
request (index 10) repeatedly debated incompatible ownership approaches; a
16-token ngram occurred nine times. Neither control wave had any request with
a 16-token ngram repeated eight times. Control request 10 progressed to an
implementation/design discussion. This is concerning evidence, not proof that
4429 alone caused the loop. Generated programs were not executed or certified.
No performance benefit justifies enabling this numerically different candidate.

## Initialization bug fixed in the experimental helper and benchmark

AIter's raw `hipb_create_extension()` allocates a 256 MiB global workspace.
Calling it directly, then calling `tuned_gemm.hipb_gemm()` while
`tuned_gemm.extensions_created` remained false, initialized it twice and lost
the first workspace pointer. Share the existing AIter initialization state.
The CPU mocked execution test checks single initialization, unsupported-solution
failure, eager warmup, capture guard, cached capture and 512 scope combinations.

Service graph allocation changed from 1.20 to 0.93 GB/GCD after the fix;
baseline is 0.65 GB/GCD. Rank-0 free memory recovered from 15.09 to 15.37 GB
(baseline 15.64 GB). The token pool stayed 1M. Remaining candidate workspace
cost is another reason not to promote a throughput-neutral implementation.
