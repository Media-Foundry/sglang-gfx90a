## Rejected instrumentation: legacy Torch/HIP profiler

`/start_profile` with `profile_by_stage=true`, `profile_stages=["decode"]`,
`num_steps=4`, CPU+GPU activities returned success. The following fixed real-code
request failed to complete normally. Eight EXTEND traces, but no DECODE traces,
appeared in `/tmp/dsv4_tp8_bs1_profile_20260907`.

The legacy profiler does not consume `profile_stages` as V2 does. Server log
`/tmp/dsv4_ck_tp8_fixed2_server.log` repeatedly reported HIP queue-interposition
signal handlers waiting for unchanged signals (over 27 million iterations).
This is an instrumentation failure, **not a decode performance measurement**;
neither a hardware fault nor a model regression has been established.

After revalidating PID 2080319 and its `sglang.launch_server` command, only its
process tree was terminated with SIGTERM. All tracked processes exited;
`amd-smi process --general --sort-by-pid` reported no running processes.

Log: `/tmp/dsv4_tp8_bs1_marker20_20260907.log`.
The marker uses `s_memrealtime`; historical calibration is 0.04 us/tick.
Require nonzero, monotonically ordered slots. Cross-stream intervals and
rank-arrival waits are not standalone operator costs. The CPU readback every
16 replays also perturbs scheduling: instrumented HTTP speed is not a new
performance checkpoint.

Historical TP8/DP2 traces and rejected multistream experiments are in
`dsv4_gfx90a_experimental_switches.md`, approximately lines 1474–1530.
They are not a direct baseline for current TP8/DP1 shard shapes.

The replacement service captured all seven graph tiers in about 11.8 s and
reached readiness. The C1 correctness harness did not complete and no valid
realtime marker log was emitted; therefore this diagnostic has no accepted
timing or correctness result. Its failure is not yet localized to marker
insertion, synchronous marker readback, or another shared startup condition.

An independent configuration issue was found: the server inherited both upper-
and lower-case HTTP/HTTPS/ALL proxy variables, with neither NO_PROXY nor
no_proxy. Python reported `proxy_bypass('127.0.0.1') == False`. The automatic
post-warmup `/freeze_gc` request uses the ambient Requests proxy configuration
and logged repeated 502s. The benchmark explicitly bypasses proxies. Thus these
502s do **not** establish an internal GC RPC deadlock. Restore the baseline
without markers, setting only process-local `NO_PROXY/no_proxy` to
`127.0.0.1,localhost,::1`, then verify ordinary inference. No global proxy or
system configuration is changed.

No new decode optimization or speedup claimed yet.

## Baseline restored and verified

Restored service log: `/tmp/dsv4_tp8_bs1_restored_20260907.log`.
No markers or Torch profiler; original large-prefill profile retained. With
process-local loopback proxy bypass, the automatic GC request reached all eight
schedulers and the detokenizer, which logged successful freezes.

Artifact: `/tmp/dsv4_tp8_bs1_restored_20260907.json`, generated by
`bench_dsv4_c1_mhc_recovery.py --arm tp8-restored --rounds 2
--skip-freeze-gc --reference /tmp/dsv4_ck_tp8_fixed2_c1.json`.

- France: both exact.
- Six measured 256-token code responses: all completion IDs equal the prior
  baseline, 6/6.
- Six fixed-continuation probes (three tasks, lengths 32 and 128): input IDs,
  returned input logprobs, output top-logprobs and next output IDs all exactly
  equal the prior baseline in the returned JSON representation.
- Measured HTTP output rates: **76.522, 76.452, 76.486, 57.820, 76.409,
  76.327 tok/s**. Median **76.430 tok/s**. The 57.820 slow sample is retained;
  its cause is not established. This is not a speedup over the previous
  77.53–77.59 smoke measurement and not an ABBA optimization comparison.
- P32 and D32 were not rerun during this diagnostic. The earlier accepted
  6420.39 input tok/s P32 result remains historical, not a measurement of this
  restart.

Production source was unchanged in this diagnostic. The known working service
is left resident on loopback port 30011. Next work must isolate marker insertion
from marker readback under the current overlap scheduler before using these
markers to choose a kernel optimization.
