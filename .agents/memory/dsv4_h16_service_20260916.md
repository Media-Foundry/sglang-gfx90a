## Execution and scope

Each same-OAM pair temporarily owns half of the query rows and all16 heads.
The Triton M16 tile then contains16 real heads instead of8 heads plus8 zero rows.
Same query, same per-head arithmetic and two-bank K16 traversal; no shared or
approximated Top-K between queries. Each rank keeps its own local KV/page mapping.

An isolated C++ extension allocates a direct-HIP512MiB Q/O buffer per rank at
capacity32768. It exports the allocation base and maps its peer's handle; there
is no caching-allocator suballocation/zero-offset assumption. Each call includes
Q staging, sink all-gather, a pair fence before compute and another after peer
output publication. All these costs are included in the service result.

Only originalV4 native TP8 ordinary large EXTEND with the existing stage1 guard
can select it. C4:M8192..32768; C128:M16384..32768. Pure-SWA layers0/1, decode,
draft, target verify, smallM and CP stay on the original path. Requires the exact
physical0..7 single-host mapping and peer access. No default enabled.

The workspace belongs to the backend runner/process. The isolated test explicitly
closes mappings before freeing the exporter allocation. Service teardown uses
owned process shutdown; live hot-reload/runner replacement is not certified.

## New independent correctness frontier: TP sink ownership

Reviewing model call sites revealed unified KV passes self.attn_sink (full64),
although _local_attn_sink() has already computed the correct local-head-first
vector. The legacy branch uses the local variable; unified forwards the full
parameter unchanged. The H8 kernel reads indices0..7 with no TP rank offset.

CPU checkpoint/captured-input audit of layer20 verifies every rank consumed
checkpoint entries0..7; TP1..7 differ from their correct8-head slice. This is
not inferred from model-generated code review text: current source, actual
captured sink values and checkpoint head slices establish the mismatch.
This is a deterministic head-ownership error, not proven explanation of
cross-run drift. H16 preserved this old baseline contract during the ABBA.
Thus8664 is a pre-correction speed result and byte exactness is only against
the existing implementation. Do not promote based on that reference alone.
Next priority is a separate local-sink correction and corrected-baseline
service verification; keep the H16 result/source snapshot separate.
