# DeepSeek-V4-Flash on gfx90a: Current Work Summary

## Current status (2026-09-11): OK

The current strict TP8 full-target DSpark configuration is accepted and healthy.
It uses the original checkpoint weights, TP8/EP1 without A2A, gamma three, the
one-million-token pool, TP synchronization for draft and accept decisions, and
the profile-local M128 MHC fusion with FP32 mixing weights. Native AR, prefill,
and the draft graph cannot enter this target-verify-only optimization.

The performance result is real and reproducible at the service level:

| family | measured resident windows | mean resident tok/s | range | mean accept length |
|---|---:|---:|---:|---:|
| Control | 4 | 1073.16 | 1058--1082 | 2.687 |
| Fusion + FP16 mixing | 4 | 1142.26 | 1131--1160 | 2.698 |
| Fusion + FP32 mixing | 4 | 1127.48 | 1118--1138 | 2.732 |

The accepted FP32 configuration improves resident throughput by **5.06%** while
holding acceptance flat to slightly higher. Its 1.8% within-family spread is
smaller than the measured effect, and the control was reproduced in two
separate arms. The FP16 result is nominally 6.44% faster than control, but it is
not statistically separable from FP32 at four windows per family, introduces a
roughly 140x larger numerical perturbation, and produced the trial's only
semantic degeneration. FP32 is therefore the production choice.

Whole-wave output hashes are not a valid determinism oracle for this trial. The
32 requests enter decode through eight chunked-prefill admissions, causing the
running batch to ramp approximately
`0 -> 1 -> 5 -> 10 -> 14 -> 19 -> 23 -> 28`. A request therefore encounters
different batch shapes depending on admission timing, so repeated waves need
not follow the same numerical execution trajectory even under greedy decoding.
This scheduling effect explains the apparent cross-round drift; it is not
evidence of an unresolved M128 correctness failure. Deterministic inference is
also unavailable for the `dsv4` attention backend.

The defensible measurement is the common resident window in which all 32
requests are decoding. Those windows lasted 12.5--13.4 seconds and contained
14,165--14,868 emitted tokens. Whole-wave throughput was dominated by admission
and drain and varied by roughly 75%, whereas resident-window spread was only
1.8--2.5%.

Both control and candidate produced coherent, on-task answers. The France
sentinel answered `Paris`. Most apparent tail repetition was `ignore_eos`
dot-padding after a completed answer, rather than semantic degeneration. The
FP32 candidate had no semantic-repetition event in its four measured windows.

In short: **the current status is OK**. The FP32 M128 MHC fusion is enabled only
for its validated strict TP8 target-verify scope, gives a defensible 5% resident
throughput improvement, preserves acceptance and observed answer quality, and
does not affect native AR or prefill.

## Earlier TP8 numerical-drift investigation (superseded diagnosis)

> The material below records the path that led to the current diagnosis. Its
> earlier BS4+/CUDA-Graph suspicion was a useful hypothesis, but it is no longer
> the current status: later resident-window analysis identified chunked
> admission and changing batch geometry as the source of the non-comparable
> cross-wave hashes.

We investigated intermittent output divergence in DeepSeek-V4-Flash on eight
MI250 GCDs under both strict full-target DSpark and native autoregressive (AR)
decoding.

The investigation initially focused on the experimental M128 down-consumer
path. Its standalone implementation was promising: the complete routed chain
improved from approximately `691.3 us` to `630.1 us`, while the
quantization-plus-down stage improved from `307.7 us` to `239.9 us`. It also
passed 100 input mutations and 1,000 HIP Graph replays bitwise. End-to-end runs,
however, still produced cross-round output drift, so the candidate remains
disabled.

Long-output testing used 32 heterogeneous code and reasoning prompts with 1,024
generated tokens per request. The France correctness sentinel remained correct,
but complete output hashes differed between rounds. Because the service exposed
only an 8,192-token KV pool, these requests were admitted in waves. The measured
`174.0` and `161.5 tok/s` values are full-request throughput and must not be
reported as resident C32 decode performance.

Several possible causes have been eliminated:

- Reusing a stable cache-salt did not remove the drift.
- Disabling M128 CK sparse attention, attention multistream execution, refined
  C4, and routed row-prefetch did not remove it.
- Disabling DSpark entirely did not remove it: native TP8 AR also diverged
  across repeated concurrent runs.

The native-AR concurrency ladder gave the strongest localization result:

| Concurrency | Cross-round result | Aggregate throughput (tok/s) |
|---:|---|---:|
| C1 | Exact | 58.60 / 62.67 |
| C2 | Exact | 83.10 / 84.05 |
| C3 | Diverged | 104.45 / 104.61 |
| C4 | Diverged | 32.07 / 139.95 (first round affected by warmup/JIT) |
| C8 | Diverged | 233.85 / 233.53 |
| C16 | Diverged | 115.09 / 116.01 |
| C32 | Diverged | 361.02 / 361.52 |

C1 and C2 were token-for-token deterministic, whereas C3 already diverged.
Since C3 is normally padded into the BS4 CUDA Graph tier, the evidence points
toward the BS4-or-larger execution path rather than checkpoint weights,
speculative acceptance, or the M128 down-consumer alone.

The leading suspects at that stage were:

1. CUDA Graph buffers shared or incompletely initialized at BS4 and above.
2. Cross-stream capture ordering or a missing event dependency.
3. A batch-sized workspace reused concurrently by multiple operators.
4. An atomic or collective reduction whose order changes with BS4 geometry.
5. A padded row leaking into a valid-row computation.

This branch of the investigation was subsequently superseded by the admission
ramp analysis above. The old concurrency ladder compared executions with
different evolving batch compositions and therefore could not establish a
BS4-or-larger correctness defect by itself.
