\begin{abstract}
本文记录 DeepSeek-V4-Flash 原生 safetensors 模型在 AMD Instinct MI250X（gfx90a/CDNA2）上的 SGLang bring-up、正确性审计和性能优化。工作覆盖 TP/EP 并行、AIter/CKTile FP4 routed MoE、FP8 dense projection、mHC、DSV4 sparse attention、HIP CUDA Graph、Mori 通信以及 OpenAI/DeepSeek Harness 协议接入。最重要的工程转折是：早期约 60 tok/s 路径后来被证明存在 routed expert 数值错误，不能作为有效性能基线；在修复 W2 行置换并建立固定 token oracle 后，正确的 TP4/EP1 原生 AR 路径最终达到约 \metric{74.5 tok/s}，4604-token prompt 的 TTFT 降至 \metric{2.061--2.062 s}。当前服务在四个 MI250X GCD 上提供 560,896-token KV pool、BS 1/2/4 decode graph 和 OpenAI-compatible tool calling。
\end{abstract}

\section{系统与模型背景}

\subsection{硬件与软件栈}

实验节点使用 AMD Instinct MI250X/MI250 的 gfx90a GCD。软件环境固定为 PyTorch \texttt{2.12.0a0+git78258b9} 与 HIP/ROCm \texttt{7.14.60850}，SGLang 与 AIter 使用本地源码。模型位于 \texttt{/home/pc/models/modelscope}，由 48 个正式 safetensors 分片组成；index 未引用的 \texttt{.incomplete} 文件不参与加载。

CDNA2 每个 CU 提供 wave64 执行模型、64 KiB LDS 和 INT8/BF16/FP16 矩阵或 dot 指令，但没有 Blackwell 类原生 FP4 matrix core。DeepSeek-V4-Flash 恰好把 routed expert 权重存为 FP4，因此 gfx90a 的关键问题不是单纯 HBM 带宽，而是小 M 条件下的 FP4 解包、scale 处理、量化、排序和同步固定成本。AMD MI200 ISA 文档是本文手写 HIP kernel 的主要硬件依据\cite{amdisa}。

\subsection{模型执行结构}

DeepSeek-V4-Flash 使用 43 个 decoder layer、256 个 routed experts、每 token top-6 routed experts，并包含 mHC、压缩注意力和 shared expert。官方模型卡说明 Flash 版本具有 284B 总参数、13B 激活参数和 1M context，expert 使用 FP4、其他主要参数使用 FP8 混合精度\cite{dsv4card}。

\section{Bring-up 与兼容工作}

最初的 ROCm 路径主要面向 gfx942/gfx950。gfx90a bring-up 包括：

\begin{itemize}[leftmargin=2em]
  \item 将 gfx90a 纳入构建目标并选择 \texttt{HIP\_FP8\_TYPE\_FNUZ}；
  \item 修复 ROCm 7.14 include/lib/rpath 探测，避免 conda host-side \texttt{hipcc} 误选；
  \item 构建 AOT HIP kernel，并补齐 AIter FP4 CK MoE 的 gfx90a 实际执行路径；
  \item 为无 RDMA NIC 节点处理 Mori topology 与 XGMI 初始化；
  \item 验证 gfx90a 上 HIP CUDA Graph capture/replay，而非把专用 kernel 误选问题归咎于硬件；
  \item 完成 TP4/EP4/Mori 与 TP4/EP1/no-A2A 两类运行路径。
\end{itemize}

早期 bring-up checkpoint 为 \commit{505b3373794a}。此后大量性能与 correctness 修改继续演进，因此该提交不是当前完整状态。

\section{正确性：从“能跑”到可信基线}

\subsection{请求 admission 与 sampler}

早期请求一直 waiting 的直接原因是 SWA admission：\texttt{max-total-tokens=4096}、\texttt{swa-full-tokens-ratio=0.1} 和 \texttt{page-size=256} 形成过小 SWA pool。提升 token pool 后请求才能进入 forward。另一个独立问题是 gfx90a AIter greedy sampler 在特殊 logits 行可能返回 \texttt{token\_id == vocab\_size}；gfx90a 因此回退到 \texttt{torch.argmax}。

DeepSeek-V4 没有 Jinja chat template，必须使用专用 encoding。官方模型卡同样明确要求使用提供的 encoding 脚本，并给出 OpenAI-compatible SGLang 调用方式\cite{dsv4card}。

\subsection{W2 行置换：旧 60 tok/s 被判无效}

\warning{旧的约 60 tok/s AIter FP4 路径不是 correctness-valid 结果。} legacy CK FP4$\times$FP4 stage-1 在 gfx90a 上输出全零；切换到 CKTile BF16$\times$FP4 后，stage-1 与 direct oracle 的 cosine 约 0.999996，但 stage-2 W2 仅约 0.24。

通过输出列指纹匹配，定位到每个 128 维 N tile 内的 16-row block 映射：

\begin{equation}
  \text{fast}\rightarrow\text{reference}=[0,2,4,6,1,3,5,7].
\end{equation}

在加载期对 raw W2 权重和 scale 应用逆置换

\begin{equation}
  [0,4,1,5,2,6,3,7]
\end{equation}

后，top-k=1 和 top-k=6 的独立 reference 检查恢复正确。该修复不增加 decode 热路径开销。

固定 France 输入 token oracle 为：

\begin{lstlisting}
[0,128803,3085,344,270,6102,294,8760,2755,128804,128822]
\end{lstlisting}

期望 completion 为：

\begin{lstlisting}
The capital of France is **Paris**.
token ids: [671,6102,294,8760,344,2619,51119,42499,1]
hash: 6f41fe2f01d52507
\end{lstlisting}

该 oracle 在 eager、decode graph 与多次独立启动中保持一致。长 prefill 的 greedy completion 仍可能从 token 0 分叉，因此下一阶段应引入 teacher-forced logits 与固定 continuation，而不是只比较整段生成 hash。

\section{Decode 优化}

\subsection{并行方式：TP4/EP1 优于 BS1 EP4}

W2 修复后，正确的 TP4/EP4+Mori BS1 仅约 14.2--15.0 tok/s。TP4/EP1/no-A2A 的 correct CKTile 对照约 20.14 tok/s，说明 BS1 下 EP4 的 dispatch/combine、rank imbalance 与 progress 固定延迟十分显著。

TP4/EP1 的最终 decode 路径包括：

\begin{itemize}[leftmargin=2em]
  \item packed FP4 权重保持 4-bit 存储；
  \item BF16 activation 每 32 元素在线量化为 INT8；
  \item E2M1 nibble 映射为 $0,\pm1,\pm2,\pm3,\pm4,\pm6,\pm8,\pm12$；
  \item 使用 CDNA2 \texttt{v\_dot4\_i32\_i8} / mixed-dot 累加，再乘 activation 与 E8M0 scale；
  \item down projection 以四个 16-lane subgroup 并行处理 top-6 slots；
  \item AIter peer-read custom all-reduce 替代高固定延迟 RCCL 路径；
  \item TP-only mHC 使用不再为 Mori progress 刻意让 CU 的几何。
\end{itemize}

\section{Prefill 优化}

\subsection{从逐 assignment 标量路径到 CDNA2 MFMA}

原始 raw-FP4 direct kernel 在 M=256 prefill 进入逐 assignment FP16 dot 分支，1028-token TTFT 约 12.9 s。优化逐步引入：

\begin{enumerate}[leftmargin=2em]
  \item 多行共享 packed FP4 权重解包，先 group8，再针对 M$\geq$1024 使用 group32；
  \item 使用 \texttt{v\_perm\_b32} LUT 替代分支式 nibble 解码；
  \item 为 M512/M1024 补齐 MI250X block-FP8 GEMM tuned config；
  \item 使用 CDNA2 INT8 MFMA 的 routed gate/down 路径；
  \item 将 sparse paged-prefill attention 从 8 wave 收缩到 1 wave；
  \item 将 chunked prefill 从 512/1024 提升到 2048；
  \item 为 M2048 调整 MFMA grid、INT8 quant HIP 专核、scale/metadata broadcast；
  \item 将 expert sorter block 从 32 提升到 64，使平均约 48 条 route 的 expert 只扫描一次 packed 权重。
\end{enumerate}

\section{实验方法与证据等级}

\subsection{资源与口径控制}

每次 GPU probe 前执行：

\begin{lstlisting}[language=bash]
amd-smi process --general --sort-by-pid -g 0 1 2 3
\end{lstlisting}

发现孤儿 scheduler、JIT worker 或非本轮 PID 时，先清理再建立基线。启动脚本拒绝非零 \texttt{SPECULATIVE\_*}，保证 native AR 口径。服务绑定 NUMA node 1，以绕过 node 0 已观测到的 host DRAM uncorrectable MCE 坏页。

\subsection{ABBA 与 trimmed median}

对可能超过 5\% 的修改使用独立服务 ABBA：

\begin{equation}
  A_1 \rightarrow B_1 \rightarrow B_2 \rightarrow A_2.
\end{equation}

每个服务先丢弃 JIT/冷 cache 首轮，再取多轮 trimmed median。微基准用于筛选候选，不能独立形成端到端结论。每轮同时记录 token 数、finish reason、HTTP wall time、server decode window 和输出 hash。

\subsection{正确性层级}

\begin{enumerate}[leftmargin=2em]
  \item kernel 级：逐元素 bitwise、max-abs、relative L2、cosine；
  \item 层级：router top-k、stage-1、activation、stage-2、rank-local sum；
  \item 模型级：France 固定 IDs 与 256-token 固定 hash；
  \item 待补：teacher-forced cached-vs-recompute logits，覆盖位置 4/128/512 及长 continuation。
\end{enumerate}

\section{服务、显存与客户端接入}

\subsection{当前部署}

当前 native AR 服务监听 \texttt{0.0.0.0:30001}，配置为 TP4/EP1、no-A2A、decode graph BS 1/2/4、\texttt{mem\_fraction\_static=1.0}。实际每 GCD 约使用 61.6/65.5 GB（约 94.1\%），KV pool 为 560,896 full tokens，graph capture 后仍保留约 4.3 GB/GCD 运行空间。

\begin{lstlisting}[language=bash]
curl http://10.120.16.9:30001/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{
    "model": "deepseek-v4-flash",
    "messages": [{"role": "user", "content": "Hello"}],
    "max_tokens": 64
  }'
\end{lstlisting}

\subsection{强制 persona 与 DeepSeek Harness}

端口 30002 是 OpenAI-compatible reverse proxy，在客户端已有 system message 的末尾强制合并服务端 persona；它支持流式转发、\texttt{/v1/models}、嵌套模型发现兼容路径与重复 chat endpoint 兼容。端口 30001 保持不注入 persona。

为 agent 工具调用启用：

\begin{lstlisting}
--tool-call-parser deepseekv4
--reasoning-parser deepseek-v4
\end{lstlisting}

非流式和流式请求均已验证返回标准 OpenAI \texttt{tool\_calls}，工具结果回送后模型能够生成最终答案。DeepSeek Harness 可配置自定义 \texttt{openai-completions} provider，并以 \texttt{/v1} 为 base URL\cite{dsh}。

\section{剩余风险与下一步}

\begin{enumerate}[leftmargin=2em]
  \item \textbf{长上下文正确性：}完成 cached decode 与 full recompute 的 teacher-forced first-divergence，重点覆盖 compressor ratio 4、SWA 128 和 indexer top-512 边界。
  \item \textbf{Indexer：}当前 full-Triton 路径仍写完整 $[B,L]$ FP32 logits，再独立 top-k。目标是 CTA-local top-512 + 二级 merge，避免 O($L$) HBM 往返。
  \item \textbf{Prefill MoE 融合：}M2048 profile 中 routed gate/up 与 down 仍占最大头部；下一步需要跨 stage 复用 activation/scale 或融合 stage1$\rightarrow$quant$\rightarrow$stage2，而不是单纯放大 MFMA tile。
  \item \textbf{Collective 边界：}peer-read AR 已优于 RCCL，但仍可尝试减少每层 collective 数量或与 epilogue 融合。
  \item \textbf{并发 parallelism：}BS1 默认 TP4/EP1；较大并发下 EP2 曾在 BS2--BS16 显示潜在收益，应在 correctness-valid 新 kernel 上重做 crossover。
  \item \textbf{运维：}将模型服务和 30002 proxy 纳入 systemd/supervisor，并处理 node 0 MCE 对应的 DIMM/EDAC 维护。
\end{enumerate}

\section{结论}

本项目的核心成果不是单一 kernel，而是建立了“正确性先行、硬件形状驱动、端到端 ABBA 验证”的 gfx90a 推理工程链路。旧 60 tok/s 结果因 routed MoE 错误被主动撤销；修复 W2、重构小 M packed-FP4$\times$INT8 decode、降低 collective 固定延迟并针对大 M prefill 使用 CDNA2 MFMA 后，正确的 native AR 达到约 74.5 tok/s，长 prefill 达到约 2.23k input tok/s。结果说明 MI250X 的主要障碍不是理论 HBM 带宽，而是 stored FP4 与 CDNA2 执行格式之间的转换、低 M 利用率以及每层同步固定成本。
