\begin{abstract}
This report documents the enablement, correctness recovery, and performance engineering of DeepSeek-V4-Flash native safetensors inference on AMD Instinct MI250 (gfx90a/CDNA2) with SGLang. The work covers TP/EP decomposition, AIter and CKTile FP4 routed mixture-of-experts (MoE), FP8 dense projections, manifold-constrained hyper-connections (mHC), DeepSeek-V4 sparse attention, HIP CUDA Graph, Mori communication, and OpenAI-compatible agent protocols. The decisive correctness finding was that an early 60 tok/s route was invalid because routed-expert computation was numerically wrong. After repairing the W2 layout, establishing fixed-token oracles, and optimizing the corrected path, TP4/EP1 native autoregressive decode reached approximately \metric{74.5 tok/s}. A 4604-token prompt reached \metric{2.061--2.062 s TTFT}, corresponding to approximately \metric{2234 input tok/s}. The current four-GCD service exposes a 560,896-token KV pool, decode graph tiers 1/2/4, streaming tool calls, and DeepSeek Harness compatibility.
\end{abstract}

\section{Related systems}

This work builds on serving systems that reduce scheduling and memory-management overhead for autoregressive language models. SGLang combines a structured runtime with RadixAttention and continuous batching, while vLLM introduced PagedAttention to manage KV-cache fragmentation and sharing efficiently\cite{sglang,vllm}. Our contribution is narrower and hardware-specific: we retain SGLang's serving abstractions while adapting the DeepSeek-V4 execution path to CDNA2 and validating optimizations against fixed-token numerical oracles.

DeepSeek-V3 established the mixture-of-experts, auxiliary-loss-free routing, multi-token prediction, and low-precision training lineage from which DeepSeek-V4-Flash evolves\cite{dsv3,dsv4card}. Systems such as MegaBlocks show how block-sparse formulations can make MoE computation practical despite irregular routing\cite{megablocks}. The present workload exposes a complementary serving regime: batch-one decode produces extremely small expert matrices, so expert layout, routing synchronization, and fixed per-layer costs matter more than large-batch sparse-GEMM throughput.

On AMD GPUs, Composable Kernel and AIter provide tuned HIP, CK, and CKTile building blocks for GEMM, quantization, attention, and MoE\cite{ck,aiter}. We use these libraries where their supported shapes are effective, but introduce gfx90a-specific paths where generic kernels do not match FP4 storage, wave64 execution, or the small-$M$ decode regime. The resulting system is therefore an integration and measurement study rather than a replacement for either the serving runtime or the kernel libraries.

\section{System and model context}

\subsection{Hardware and software stack}

The experimental host is a Supermicro A+ Server AS-4124GQ-TNMI with two AMD EPYC 7763 processors and SMT enabled. Host memory comprises 32 32-GiB DDR4-2933 2Rx8 RDIMMs, for 1 TiB installed capacity. The deployment uses four visible AMD Instinct MI250 gfx90a GCDs. The software environment is fixed to PyTorch \texttt{2.12.0a0+git78258b9} and HIP/ROCm \texttt{7.14.60850}, with local SGLang and AIter source trees. The model at \texttt{/home/pc/models/modelscope} consists of 48 indexed safetensors shards. Residual \texttt{.incomplete} files are not referenced by the index and are not loaded.

CDNA2 provides wave64 execution, 64 KiB LDS per CU, and INT8/BF16/FP16 matrix or dot instructions, but no native FP4 matrix core comparable to newer accelerator generations. DeepSeek-V4-Flash stores routed-expert weights in FP4. Consequently, the critical gfx90a cost is not raw HBM bandwidth alone: it is the combination of small-M utilization, online FP4 unpacking, scale handling, activation quantization, expert sorting, and layer-level synchronization. The AMD MI200 ISA manual guided the custom HIP kernels in this work\cite{amdisa}.

\subsection{Execution structure}

DeepSeek-V4-Flash has 43 decoder layers, 256 routed experts, top-6 routing per token, shared experts, mHC, and compressed sparse attention. The official model card reports 284B total parameters, 13B active parameters, a one-million-token context, and mixed FP4 expert / FP8 non-expert precision\cite{dsv4card}.

\section{gfx90a enablement}

The original ROCm path primarily targeted gfx942 and gfx950. The gfx90a bring-up required the following changes:

\begin{itemize}[leftmargin=2em]
  \item add gfx90a as a build target and select \texttt{HIP\_FP8\_TYPE\_FNUZ};
  \item repair ROCm 7.14 include, library, and rpath discovery while avoiding the conda host-side \texttt{hipcc};
  \item build AOT HIP kernels and enable AIter FP4 CK MoE execution on gfx90a;
  \item handle Mori topology and XGMI initialization on a node without an RDMA NIC;
  \item validate HIP CUDA Graph capture and replay on gfx90a instead of attributing architecture-specific kernel selection failures to the hardware;
  \item establish both TP4/EP4 with Mori and TP4/EP1 without A2A as executable reference paths.
\end{itemize}

The initial bring-up checkpoint was \commit{505b3373794a}. It predates the later correctness and performance work and must not be treated as the final state.

\section{Correctness recovery}

\subsection{Admission, sampling, and chat encoding}

An early request stall was an SWA admission failure rather than a Mori or RCCL deadlock. The combination of \texttt{max-total-tokens=4096}, \texttt{swa-full-tokens-ratio=0.1}, and \texttt{page-size=256} produced a pool below the admission floor. A separate gfx90a AIter greedy-sampler issue could return \texttt{token\_id == vocab\_size} on special logits rows; gfx90a now uses \texttt{torch.argmax} for this case.

DeepSeek-V4 does not ship a Jinja chat template. It requires the model-specific encoding and output parser, which is also stated in the official model card\cite{dsv4card}.

\subsection{W2 permutation: invalidating the early 60 tok/s result}

\risk{The early approximately 60 tok/s AIter FP4 route was not correctness-valid.} The legacy CK FP4-by-FP4 stage-1 path produced zeros on gfx90a. After switching to CKTile BF16-by-FP4, stage 1 reached approximately 0.999996 cosine similarity to a direct oracle, but stage-2 W2 remained near 0.24.

Output-column fingerprinting identified the following 16-row block mapping within each 128-wide N tile:

\begin{equation}
  \text{fast}\rightarrow\text{reference}=[0,2,4,6,1,3,5,7].
\end{equation}

Applying the inverse permutation

\begin{equation}
  [0,4,1,5,2,6,3,7]
\end{equation}

to raw W2 weights and scales during loading restored the logical output order for top-k=1 and top-k=6. This is a one-time load transformation with no decode hot-path cost.

The fixed France oracle uses the following input IDs:

\begin{lstlisting}
[0,128803,3085,344,270,6102,294,8760,2755,128804,128822]
\end{lstlisting}

Its expected completion is:

\begin{lstlisting}
The capital of France is **Paris**.
token ids: [671,6102,294,8760,344,2619,51119,42499,1]
hash: 6f41fe2f01d52507
\end{lstlisting}

The oracle is stable across eager execution, decode graph replay, and independent service starts. Long-prefill greedy completions can still diverge from token zero, so the next validation tier must use teacher-forced logits and fixed continuations rather than whole-completion hashes alone.

\section{Decode optimization}

\subsection{Parallel decomposition}

After the W2 repair, the correct TP4/EP4+Mori BS1 baseline was only 14.2--15.0 tok/s. The TP4/EP1 no-A2A CKTile reference reached approximately 20.14 tok/s. This established that expert dispatch/combine, rank imbalance, and communication progress overhead dominate BS1 EP4.

The final TP4/EP1 decode route combines:

\begin{itemize}[leftmargin=2em]
  \item packed 4-bit FP4 weights without an offline expansion;
  \item online BF16 activation quantization to INT8 per 32 elements;
  \item E2M1 nibble mapping to $0,\pm1,\pm2,\pm3,\pm4,\pm6,\pm8,\pm12$;
  \item CDNA2 \texttt{v\_dot4\_i32\_i8} / mixed-dot accumulation followed by activation and E8M0 scaling;
  \item four 16-lane subgroups for top-6 slots in the down projection;
  \item AIter peer-read custom all-reduce in place of the high fixed-latency RCCL path;
  \item TP-only mHC launch geometry that no longer reserves CUs for Mori progress.
\end{itemize}

\section{Prefill optimization}

\subsection{From per-assignment scalar work to CDNA2 MFMA}

The original raw-FP4 direct kernel sent M=256 prefill through a per-assignment FP16 dot path, with approximately 12.9 s TTFT for a 1028-token prompt. The optimization sequence introduced:

\begin{enumerate}[leftmargin=2em]
  \item packed-FP4 unpack reuse across rows, first group8 and then group32 for M$\geq$1024;
  \item \texttt{v\_perm\_b32} lookup tables instead of branch-heavy nibble decoding;
  \item MI250 block-FP8 tuned configurations for M512 and M1024 dense projections;
  \item CDNA2 INT8 MFMA routed gate and down kernels;
  \item sparse paged-prefill attention reduction from eight waves to one wave;
  \item chunked-prefill growth from 512/1024 to 2048;
  \item M2048-specific MFMA grids, native HIP INT8 quantization, and scale/metadata broadcast;
  \item an expert sorter block increase from 32 to 64 rows, allowing an expert with approximately 48 assignments to scan packed weights once.
\end{enumerate}

\section{Measurement methodology}

\subsection{Resource and metric controls}

Every GPU experiment begins with:

\begin{lstlisting}[language=bash]
amd-smi process --general --sort-by-pid -g 0 1 2 3
\end{lstlisting}

Measurements are rejected when unexpected scheduler, compiler, profiler, or model processes remain on the target GCDs. The native-AR harness rejects nonzero \texttt{SPECULATIVE\_*} variables. The experimental host had a known node-0 memory fault; therefore, all accepted measurements were pinned to NUMA node 1. This host condition is independent of the MI250 accelerators and SGLang software under evaluation.

\subsection{ABBA and trimmed medians}

Changes expected to exceed 5\% use independent service starts in the sequence

\begin{equation}
  A_1 \rightarrow B_1 \rightarrow B_2 \rightarrow A_2.
\end{equation}

The JIT/cold-cache first round is excluded, and repeated rounds are summarized with a trimmed median. Each run records actual completion length, finish reason, HTTP wall time, server decode window, and output hash.

\subsection{Correctness hierarchy}

\begin{enumerate}[leftmargin=2em]
  \item Kernel level: elementwise bitwise equality, maximum absolute error, relative L2, and cosine similarity.
  \item Layer level: router top-k, stage 1, activation, stage 2, and rank-local sum.
  \item Model level: France fixed IDs and the 256-token fixed trajectory hash.
  \item Planned: teacher-forced cached-vs-recompute logits at compressor-4, SWA-128, and indexer-512 boundaries.
\end{enumerate}

\section{Serving, memory, and agent integration}

\subsection{Current deployment}

The native AR server listens on \texttt{0.0.0.0:30001}. It runs TP4/EP1 without routed-expert A2A, uses decode graph tiers 1/2/4, and sets \texttt{mem\_fraction\_static=1.0}. Each GCD uses approximately 61.6/65.5 GB (94.1\%). The full-token KV pool is 560,896, while graph capture leaves approximately 4.3 GB/GCD runtime headroom.

\begin{lstlisting}[language=bash]
curl http://127.0.0.1:30001/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{
    "model": "deepseek-v4-flash",
    "messages": [{"role": "user", "content": "Hello"}],
    "max_tokens": 64
  }'
\end{lstlisting}

\subsection{Forced persona and DeepSeek Harness}

Port 30002 is an OpenAI-compatible reverse proxy. It appends a server-owned persona to an existing system message or inserts one when absent. It preserves streaming, tools, model discovery, and compatibility aliases. Port 30001 remains free of persona injection.

Agent protocol support is enabled with:

\begin{lstlisting}
--tool-call-parser deepseekv4
--reasoning-parser deepseek-v4
\end{lstlisting}

Both streaming and non-streaming requests return standard OpenAI \texttt{tool\_calls}; a second request containing the tool result produces the final assistant response. DeepSeek Harness can use either endpoint as a custom \texttt{openai-completions} provider with \texttt{/v1} as its base URL\cite{dsh}.

\section{Remaining risks and next steps}

\begin{enumerate}[leftmargin=2em]
  \item \textbf{Long-context correctness.} Add teacher-forced cached-vs-full-recompute first-divergence tests around absolute positions 4, 128, and 512.
  \item \textbf{Indexer traffic.} Replace the current full $[B,L]$ FP32 logits write plus separate top-k read with CTA-local top-512 candidates and a second-stage merge.
  \item \textbf{Prefill MoE fusion.} Reuse activation and scale state across stage 1 and stage 2, or fuse stage1$\rightarrow$quant$\rightarrow$stage2. Merely enlarging an MFMA tile has already been disproven.
  \item \textbf{Collective boundaries.} Peer-read all-reduce is superior to RCCL, but the layer still benefits from fewer collectives or epilogue fusion.
  \item \textbf{Concurrency crossover.} BS1 favors TP4/EP1. EP2 showed exploratory gains at larger concurrency and should be re-evaluated on the corrected routed-MoE path.
  \item \textbf{Operations.} Place both the model service and port-30002 proxy under systemd or a supervisor. The known node-0 host-memory fault should be serviced separately; accepted measurements remain pinned to node 1 until then.
\end{enumerate}

\section{Conclusion}

The principal result is not a single kernel but a reproducible gfx90a inference workflow built around correctness-first validation, hardware-shape-driven optimization, and endpoint-level ABBA tests. The project explicitly withdrew an attractive but incorrect 60 tok/s result. After W2 recovery, small-M packed-FP4-by-INT8 decode, lower collective latency, and large-M CDNA2 MFMA prefill work, the corrected native AR path reached approximately 74.5 tok/s and long prefill reached approximately 2.23k input tok/s. The evidence indicates that MI250 is limited less by nominal aggregate HBM bandwidth than by the mismatch between stored FP4 and CDNA2 execution formats, low-M utilization, and fixed synchronization costs per layer.
